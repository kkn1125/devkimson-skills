# 코드 기반 UI 검토

## 연결된 구현을 읽는다

프로젝트 지침과 이미 사용하는 UI 시스템을 확인한다. 모든 파일을 읽기보다 대상 화면의 연결을 따라간다.
컴포넌트 → 공용 컴포넌트/스타일 → 테마·토큰 → 호출부·상태·이벤트 → 관련 테스트 순서에서 판단에 필요한 부분만 읽는다.
PR이라면 변경 줄과 관련 기존 구현을 함께 본다. 공유 컴포넌트 수정 제안은 다른 호출 화면에 미칠 영향도 확인한다.
라이브러리 래퍼가 이름·포커스·키보드 처리를 제공할 수 있으므로 JSX 한 줄만 보고 누락을 단정하지 않는다.
버전별 동작을 확신하지 못하면 설치된 버전과 공식 문서를 확인한다. 스택을 모르면 특정 프레임워크 도입을 전제하지 않는다.

## 검토할 연결

| 영역 | 필요한 근거 |
| --- | --- |
| 상태 | 로딩·빈 결과·오류·부분 성공·권한 없음·선택 상태의 분기 |
| 액션 | 이벤트 연결, 비활성 조건, 중복 제출, 행 클릭과 내부 버튼의 충돌 |
| 폼 | label·설명·오류 연결, 검증 시점, 입력 보존, 완료 피드백 |
| 탐색 | 현재 위치, 링크/버튼 의미, 뒤로 가기·필터 보존 |
| 레이아웃 | 토큰, 폭·최소폭, 줄바꿈·overflow, 반응형 분기, fixed/sticky 영향 |
| 접근성 | 실제 요소·이름·상태, 키보드 경로, focus-visible·모달 처리 |
| 테마 | 하드코딩 색, 상속·우선순위, disabled/hover/focus/selected 상태 |

`outline: none`은 대체 포커스 표시까지 확인한 뒤 평가한다.
아이콘 버튼의 `aria-label`이 안 보여도 자식 텍스트·`aria-labelledby`·공용 컴포넌트가 이름을 제공할 수 있다.
UI에서 권한에 따라 버튼을 숨기는 코드는 서버 인가를 증명하지 않는다. 필요한 경우 별도 보안 확인으로 연결한다.
성능은 사용자에게 보이는 지연·끊김의 근거가 있을 때만 관련 경로를 검토한다. 코드 형태만 보고 렌더링 지연 수치를 만들지 않는다.

## 정적 판단과 실행 판단

“코드: 320px에서 최소폭 640px 유지”와 “관찰: 모바일에서 화면 밖으로 저장 버튼이 나감”을 구분한다.
스타일 선언은 cascade·컨테이너·폰트·콘텐츠에 영향을 받는다. 코드만으로 실제 픽셀·대비·모든 뷰포트 동작을 확정하지 않는다.
기존 테스트가 있어도 실행하지 않았다면 “테스트 구현 확인”이라고만 적는다.
빌드 통과는 시각적 완성도나 키보드 사용성 검증이 아니다.

브라우저가 제공되고 실행이 허용되면 [브라우저 검토](browser-review.md)에 따라 문제 후보에 맞는 최소 재현을 확인한다.
예: 좁은 폭에서 긴 값 → 메뉴 열기 → 키보드 이동 → 확대 상태의 잘림 확인.
브라우저가 없으면 코드로 확인한 범위와 남은 실행 확인을 표시하고 완료한다.
검토를 위해 패키지 설치·소스 수정·새 테스트 생성이 필요하면 그것이 사용자 요청에 포함되는지 먼저 판단한다.
기존 읽기 전용 검사를 실행할 수 있어도 예상 부작용과 실제 데이터를 먼저 확인한다.

## 결과 위치와 수정 전환

검증한 실제 파일·줄과 연결된 원인을 적는다. 제공되지 않은 저장소 경로·줄 번호는 만들지 않는다.
문제 하나에 필요한 최소 변경 범위를 제안하되 검토만 요청받았다면 diff를 적용하지 않는다.
사용자가 “고쳐줘”라고 이미 요청했다면 명시된 범위에서 프로젝트 구현 규칙으로 진행한다. 검토 스킬을 근거로 같은 승인을 다시 요구하지 않는다.
검토를 넘어 백엔드·데이터·배포 변경이 필요하면 추가 범위를 분명히 한다.
