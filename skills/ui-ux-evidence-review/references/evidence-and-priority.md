# 증거와 우선순위

## 근거 유형은 확신도의 순위가 아니다

| 표기 | 사용할 때 | 그 근거가 증명하지 않는 것 |
| --- | --- | --- |
| 관찰 | 캡처에서 읽거나 실제 화면에서 직접 재현 | 다른 뷰포트·상태·사용자에게도 같은 결과인지 |
| 코드 | 파일·줄·연결된 구현을 확인 | 실제 렌더링·실행 순서·서비스 응답 결과 |
| 측정 | 도구·입력·조건·결과를 기록 | 측정하지 않은 상태나 전체 서비스 준수 |
| 가설 | 일부 근거와 사용자 영향 추론 | 실제 발생 여부·빈도·운영 영향 |

“관찰: 모달 밖으로 포커스 이동, Chrome·키보드·테스트 화면”과 “코드: 포커스 복귀 로직이 보이지 않음”은 서로 다른 주장이다.
캡처에서 보이는 버튼을 확실히 식별할 수 있어도 실제 클릭 동작까지 확신할 수는 없다.

## 주장에 맞춰 확신도를 정한다

- **높음:** 해당 주장에 필요한 자료가 직접 확인됐고 중요한 다른 설명이 배제됐다.
- **중간:** 관련 근거는 있지만 상태·사용량·구현 연결 중 일부가 빠졌다. 조건부 표현을 쓴다.
- **낮음:** 추정이 핵심이다. 확정 결함 대신 “확인 필요”에 넣고 필요한 자료를 특정한다.

관찰 사실과 사용자 영향을 분리한다. “3개 행이 보임”은 관찰, “처리 시간이 길어짐”은 작업량 정보가 없으면 가설이다.
화면에 “미읽음 49”가 보여도 실제 담당자의 처리량·활성 목록 수·페이지네이션은 따로 확인한다.
자동화 검사 결과는 해당 규칙의 결과로 기록한다. 검사 통과를 스크린리더 사용성이나 전체 WCAG 준수로 확대하지 않는다.

## 우선순위

| 등급 | 사용 영향 | 기본 대응 |
| --- | --- | --- |
| P1 | 핵심 작업을 막음, 큰 오조작·복구 불가 손실, 특정 입력 방식의 핵심 작업 배제 | 먼저 해결하거나 영향 큰 가설을 먼저 검증 |
| P2 | 반복 작업의 실질적 마찰·오해·누락, 우회나 복구 가능 | 다음 수정 범위에 포함 |
| P3 | 영향이 작거나 드문 상황의 명확한 개선 | 여유가 있을 때 처리 |

P1은 배포 차단 여부를 자동으로 뜻하지 않는다. 출시 판단은 사용 범위·프로젝트 기준으로 별도 결정한다.
심각도, 노출 범위, 발생 빈도, 복구 비용을 고려하되 수치를 모르면서 곱셈 점수를 만들지 않는다.
다수 사용자에게 드물게 일어나는 문제와 소수 사용자에게 항상 막히는 문제를 모두 고려한다.
수정 노력은 처리 순서를 조정할 수 있지만 문제 자체의 심각도를 낮추는 이유는 아니다.
확신도가 낮고 영향이 크면 “P1 가능성 · 검증 우선”으로 표시한다. 단순히 P3로 낮춰 숨기지 않는다.

## 과잉 진단을 거르는 질문

1. 관찰 가능한 위치와 사실이 있는가?
2. 이 사용자의 작업에 어떤 비용·오류·배제가 생기는가?
3. 제품 의도·기존 패턴·다른 상태로 설명될 수 있는가?
4. 제안이 더 큰 발견성·접근성·일관성 문제를 만들지 않는가?
5. 지금 자료에서 확정할 수 있는 주장과 필요한 확인을 나눴는가?

다섯 질문을 통과하지 못하는 후보를 개수 채우기용으로 내보내지 않는다.
“업무 UI는 반드시 작아야 한다”, “메뉴는 7개 이하”, “배지는 색이 달라야 한다” 같은 규칙만으로 결함을 만들지 않는다.

## 자료가 충돌할 때

코드와 캡처의 버전·테마·권한·데이터·폭을 대조한다. 서로 다른 자료라면 각각의 범위에서만 말한다.
원인을 못 찾으면 모순을 기록하고 확인 항목으로 남긴다. 어느 한쪽이 최신이라고 임의로 선택하지 않는다.
검토가 끝나면 새 정보가 있어야 같은 영역을 다시 검사한다. 변화 없는 탐색을 반복하지 않는다.
