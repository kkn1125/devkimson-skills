# 관리자·업무용 UI

## 역할과 반복 작업

운영 담당자·승인자·관리자의 핵심 행동을 구분한다. 많이 쓰는 사람과 처음 쓰는 사람에게 필요한 안내가 다를 수 있다.
운영 규모·일일 처리량을 모르면 가정으로 남긴다. 행 수·카드 크기만으로 생산성 수치를 계산하지 않는다.

## 목록·테이블·알림

- 제목·식별자·상태·핵심 날짜를 빠르게 비교할 수 있는가. 모든 정보를 같은 강조로 두지 않는다.
- 검색·필터의 범위와 활성 조건이 보이는가. 조건 초기화와 결과 없음의 복구 경로가 있는가.
- 정렬 방향, 페이지 크기, 전체 수와 현재 범위가 필요한 만큼 드러나는가.
- 행 선택과 상세 진입이 구분되는가. 선택 수와 액션 대상이 실행 전 명확한가.
- 필터·정렬·페이지 이동 후 선택이 유지되는지, 초기화되는지 실제 근거로 확인한다.
- “전체 선택”이 현재 페이지인지 필터 결과 전체인지 명시되는가. 수천 건 작업 가능성은 제품 조건을 확인한다.
- 일괄 처리의 부분 실패·재시도·결과 요약이 필요한가. 성공 토스트 하나로 모든 행 성공을 단정하지 않는다.

알림은 훑기 → 처리 필요 판단 → 이동/읽음 처리 흐름을 본다.
읽음/미읽음은 텍스트·굵기·형태 등으로 구분하되 모든 신호를 동시에 넣을 필요는 없다.
행마다 반복되는 읽음/삭제 액션은 노이즈와 발견성의 비용을 비교한다.
큰 행을 줄일 때 긴 제목·출처·필수 메타정보·터치 영역을 보존한다.

## 폼과 위험한 작업

저장·승인·삭제·권한 변경의 대상과 효과를 구분한다. 주 액션 근처의 보조 액션이 오조작을 만드는지 본다.
변경 내용, 되돌릴 수 있는지, 대량 적용 범위가 중요한 작업에서는 실행 전에 확인할 수 있어야 한다.
권한 없는 이유와 요청 경로는 필요한 범위에서 제공하되 UI 문구가 민감한 정보나 불필요한 계정 정보를 노출하지 않는지 확인한다.
역할별 표시를 서버 인가의 증거로 사용하지 않는다.
실제 운영 계정으로 삭제·승인·발송을 재현하지 않는다. 안전한 테스트 환경이 없으면 구현 확인과 미확인 동작을 구분한다.

## 대시보드

KPI가 어떤 기간·단위·기준시각의 값인지, 비교 기준과 데이터 갱신 시점이 판단에 필요한지 본다.
표시된 수치를 사실로 읽되 실제 데이터 정확성은 API·조회 조건 등의 별도 근거가 있어야 확인할 수 있다.
차트가 우선순위 판단·이상 발견·다음 작업 진입을 돕는지 살핀다. 장식 차트를 늘리지 않는다.
상태색·축·범례·단위가 오해를 만드는지, 툴팁에만 핵심 값이 숨었는지 확인한다.

## 업무 UI의 접근성·좁은 화면

단순 표와 상호작용 그리드를 구분한다. 복잡한 그리드의 키보드 탐색은 적용된 컴포넌트 패턴을 확인한다.
모든 셀을 Tab 정류장으로 늘리는 것을 기본 해결책으로 삼지 않는다.
데이터 표의 가로 스크롤이 필요한 경우에도 검색·주 액션·페이지 전체의 가로 넘침을 별도로 본다.
모바일에서 카드로 바꾸면 열 간 비교가 더 어려워지는지 확인한다. 사용자 작업과 제품 지원 범위에 맞춰 결정한다.
밀도 변경, 열 고정, 가상 스크롤 제안에는 포커스·읽기 순서·전체 값 접근의 확인을 붙인다.

참고: [WAI-ARIA APG Grid Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/grid/)은 상호작용 그리드의 구현 지침이다. 모든 표에 `role="grid"`를 강제하는 규정이 아니다.
