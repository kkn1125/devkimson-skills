# 다크모드·테마

## 어두운 배경이라는 이유로 문제를 만들지 않는다

순수 검정·순수 흰색, 높은 대비, 그림자 사용은 그 자체로 결함이 아니다.
눈부심·층 구분·가독성 문제는 해당 화면의 콘텐츠와 사용 조건에 연결한다. 개인 선호를 접근성 위반이라고 말하지 않는다.
밝은 테마를 보지 않았다면 “다크 테마 관찰 범위”로 한정한다. 제공되지 않은 테마를 추정하지 않는다.

## 판단할 관계

| 관계 | 살필 내용 |
| --- | --- |
| 배경 → 표면 → 떠 있는 패널 | 실제 경계·배경·명도 변화로 구조를 구분할 수 있는가 |
| 본문 → 보조 정보 → 비활성 | 필요한 정보가 opacity 감소로 읽기 어려워졌는가 |
| 기본 → hover → focus → selected → error | 각 상태가 구분되며 의미가 테마 간 유지되는가 |
| 상태색·배지·차트 | 텍스트·패턴·형태가 의미를 보완하는가 |
| 아이콘·로고·이미지 | 밝은 테마용 자산이 배경에 묻히거나 흰 사각형을 만드는가 |
| 팝업·스크롤바·입력 컨트롤 | 주변 테마와 분리되어 사용 맥락을 끊는 실제 현상이 있는가 |

카드·구분선을 무조건 추가하기보다 기존 표면 토큰과 정렬을 이용할 수 있는지 본다.
색 하나를 밝히기 전에 인접 배경·상태·본문과의 관계를 확인한다.
선택과 오류를 배경색 하나로만 표시하면 다른 신호를 추가하는 방향을 검토한다.
상태마다 다른 색을 추가할 필요는 없다. 텍스트가 의미를 충분히 전달하면 같은 중립색도 적절하다.

## 코드·측정이 있을 때

테마 토큰·상속·하드코딩 색·반투명 레이어의 실제 합성을 확인한다.
대비 수치와 적용 기준은 [접근성](accessibility.md)을 선택해 확인한다. 스크린샷에서 추측한 hex값을 정확한 computed color처럼 사용하지 않는다.
다크모드 수정을 제안할 때 같은 토큰을 쓰는 밝은 테마·hover·disabled·focus 상태의 회귀 가능성을 적는다.
테마 전환의 깜박임·선택 저장·시스템 설정 반영은 동작 근거가 있을 때만 평가한다.
테마 자동 선택·전환 기능 자체는 사용자 요청이나 제품 요구가 없다면 새 기능으로 제안하지 않는다.

## 최소 확인

문제 후보가 있는 요소의 기본·포커스·선택·오류 상태부터 확인한다.
같은 콘텐츠와 상태의 밝은/어두운 테마 자료가 있으면 비교한다. 하나만 있으면 나머지는 미확인으로 남긴다.
가독성 제안은 실제 색상 쌍과 텍스트 크기가 있을 때 측정으로 보완한다. 전체 색상 팔레트 교체를 기본안으로 삼지 않는다.
