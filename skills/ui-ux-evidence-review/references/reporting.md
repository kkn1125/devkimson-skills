# 결과 보고와 재검토

## 길이는 발견에 맞춘다

한 가지 문제면 결론·근거·개선안·확인 조건을 한두 문단으로 작성한다.
여러 발견이면 중요한 순으로 짧게 나눈다. 사용자에게 불필요한 라우팅 파일 목록이나 내부 절차를 출력하지 않는다.
기본 핵심 1~3개는 분량 가이드이며 실제 중요한 문제를 생략하는 상한이 아니다.
별도 총점, 채우기용 장점·단점, 모든 체크 항목의 통과 표시는 기본 출력에 넣지 않는다.
종합/컴포넌트 검토에서는 [구조와 컴포넌트](structure-and-components.md)의 사용 목록 → 컴포넌트별 표 → 별도 디자인 토큰 정리를 포함한다. 포커스 검토에서는 [인터랙션 검토](interaction-review.md)의 문제 모달 전체 목록과 미확인 대상을 포함한다. 요약의 분량 가이드로 이 산출물을 생략하지 않는다.

## 발견 하나의 구조

**[P2 · 관찰 · 확신 중간] 캡처 1, 알림 목록: 한 화면의 비교 정보가 적음**

제공된 화면에는 알림 3개가 보이며 각 행에 같은 보조 버튼이 반복된다. 대량 처리 화면이라면 항목 간 비교와 미처리 탐색에 스크롤 비용이 생길 수 있다.
반복 버튼과 중복 메타정보를 정리하고 기존 행 패딩을 한 단계 줄이는 안부터 확인한다. 주요 액션의 키보드·터치 접근은 유지한다.
실제 처리량과 긴 제목 상태는 미확인이다. 긴 항목을 포함한 목록에서 가시 행 수와 필요한 정보 손실을 비교하면 제안을 확인할 수 있다.

예시의 행 수·우선순위를 다른 화면에 그대로 복사하지 않는다.
측정 결과라면 입력·도구·조건·값·적용 기준을 적고, 코드 근거라면 실제 파일·줄을 적는다.
사용 영향을 직접 실험하지 않았다면 관찰 결과와 추론을 한 문장으로 섞지 않는다.

## 결론에 넣을 것

- 화면 목적과 가장 중요한 진단. 중요한 문제가 없으면 확인 범위에서 없다고 말한다.
- 유지할 장점이 실제로 확인됐다면 한두 줄. 수정안이 그 장점을 보존하게 한다.
- 바로 할 수정과 먼저 할 확인을 구분한다. 낮은 확신의 큰 영향 가설은 “검증 우선”으로 적는다.
- 미확인 사항은 결과를 바꿀 항목만 남긴다. 자료 부족을 장황한 면책 문구로 늘리지 않는다.

사용자가 이미 수정을 요청하지 않았다면 구현 완료처럼 말하지 않는다.
모든 결과 뒤에 “원하면 고쳐드릴게요”를 기계적으로 붙이지 않는다.
기존 보고서와 재검토를 비교할 때는 해결·잔존·새 문제·미확인을 실제 새 근거에 맞춰 표시한다.

## PR·코드 의견

검증한 위치의 행동과 사용자 영향을 설명한다. 수정 예시를 요청받지 않았다면 긴 대체 코드를 붙이지 않는다.
같은 공용 원인의 여러 증상은 대표 위치와 영향 화면으로 합친다.
줄이 바뀌었으면 현재 버전 위치를 다시 확인한다. 화면에서 확인한 문제를 관계없는 코드 줄에 붙이지 않는다.
브라우저 확인 없이 “화면 확인 완료”, 테스트 실행 없이 “통과”, 패치 적용 없이 “수정 완료”라고 말하지 않는다.
