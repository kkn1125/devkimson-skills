# 화면 구조·메뉴 IA·컴포넌트 검토

## 반복 행동이 판단 기준이다

화면을 평가하기 전에 `주요 사용자 / 자주 하는 행동 / 빈도 근거 / 진입점 / 완료 조건`을 짧게 정리한다.
조회·검색·알림 확인·작성·수정·승인 등 실제 제공된 행동을 사용한다. 빈도는 사용자 설명이나 사용 기록을 우선하며 모르면 가정으로 남긴다.
반복 행동의 발견·이동·입력·비교·결과 확인·복구가 편한지를 기준으로 배치를 판단한다. 클릭 수만으로 사용성을 판정하거나 측정하지 않은 시간 절감률을 만들지 않는다.

## 전체 구조와 일관성

- 사이드바·헤더·콘텐츠·보조 패널의 역할, 폭/높이 배분, 현재 위치와 주 액션의 발견성을 확인한다.
- 요소 크기·간격·정렬·텍스트 줄 수·정보 밀도가 반복 행동에 맞는지 본다. 입력/필터가 실제 목록보다 과도한 비중을 차지하는지 비교한다.
- 접힌/펼친 사이드바, 고정 헤더/버튼, 좁은 폭·짧은 높이에서 본문 축소·겹침·스크롤 범위를 확인한다. 특정 폭의 관찰을 전체 기기로 일반화하지 않는다.
- 화면 간 같은 의미의 용어·아이콘·버튼 위치·위계·상태 표현을 대조한다. 서로 다른 작업의 정당한 차이까지 획일화하지 않는다.
- 같은 자료와 조건에서 전후를 비교한다. 고정 픽셀 규칙이나 새로운 디자인 시스템을 기본 해결책으로 삼지 않는다.

## 메뉴 구조(IA)와 보조 진입점

사이드바 메뉴뿐 아니라 헤더/레일 아이콘, 드롭다운, 팝오버, 빠른 실행, 페이지 링크를 함께 목록화한다.
각 진입점의 목적지·주 행동·제공 정보·현재 위치/상태 표시를 대조하여 중복과 보완 관계를 구분한다.

- 예: 사이드바 알림함과 접힌 레일의 알림 아이콘은 중복 후보다. 아이콘이 최근 알림 미리보기이고 페이지가 전체 이력·검색·필터라면 역할이 다르므로 이름만 보고 하나를 삭제하지 않는다.
- 알림·메일처럼 자주 확인하는 항목은 현재 작업을 유지하는 드롭다운/팝오버가 나은지 검토한다. 긴 본문·검색·대량 처리·첨부 등에는 전체 화면이 필요할 수 있다. 미리보기와 ‘전체 보기’를 함께 유지하는 안도 비교한다.
- 팝오버 전환은 이동 비용뿐 아니라 발견성, 키보드/터치 접근, 초점 처리, 긴 내용·빈 상태·실패, URL/직접 링크·새 탭 접근의 손실을 비교한다. 확인 동작의 읽음 처리 같은 부작용도 검토 범위와 맞춘다.
- 사용 빈도와 업무 개념을 기준으로 그룹·순서·상위 메뉴/하위 메뉴를 제안한다. 빈도 자료가 없으면 잠정 순서라고 밝힌다. 메뉴 개수만으로 재구성하거나 드문 필수 기능을 숨기지 않는다.
- 이동/통합 제안에는 현재 진입점 → 권장 위치·역할 → 유지할 전체 화면/기능 → 적용 조건을 적는다. 사용자별 권한·숨김 메뉴를 확인하지 않았으면 전체 제품의 메뉴 목록이라고 말하지 않는다.

메뉴 정리가 요청되면 `현재 진입점 / 대상 행동·정보 / 중복 또는 보완 / 빈도 근거 / 권장 그룹·순서·진입 방식`으로 비교한다.

## 컴포넌트 목록을 만든 뒤 점검한다

실제 화면에 쓰인 재사용 대상과 사용 위치를 먼저 정리한다. 버튼, 인풋, 셀렉트, 탭, 배지, 카드/목록 행, 모달, 드롭다운, 토스트, 빈 상태, 사이드바 메뉴 항목 등을 빠뜨리지 않되 없는 컴포넌트를 만들어 채우지 않는다.
소스가 있으면 공용 컴포넌트·래퍼·호출부·테마/토큰을 연결한다. 소스가 없으면 같은 시각 패턴이라는 관찰과 공용 구현이라는 추정을 구분한다.

각 컴포넌트의 해당 상태·변형에 대해 다음을 확인한다.

| 점검 | 확인할 내용 |
| --- | --- |
| 화면 간 동일성 | 같은 역할/크기/변형인데 높이·패딩·라운드·폰트 크기·색·아이콘 배치가 달라지는가. 호출부 덮어쓰기와 테마를 확인한다. |
| 상태 | default / hover / focus / active / disabled / loading / error / empty를 검토하고 적용·확인·미확인·비대상 이유를 구분한다. 눌림(active)과 지속 선택(selected)을 필요할 때 따로 본다. |
| 변형과 크기 | primary / secondary / ghost / danger의 역할 구분과 sm/md/lg 크기 규칙이 프로젝트에서 일관되는가. 실제 이름이 contained/outlined/text 또는 small/medium/large라면 그 대응을 기록하고 이름 변경을 강제하지 않는다. |
| 용도에 맞는 비율 | 입력/필터·버튼·행·카드의 크기와 텍스트량이 비교·입력·조작 목적에 맞는가. 목록보다 과하게 큰 입력, 내용에 비해 큰 카드와 빈 공간을 확인한다. |
| 통합 또는 분리 | 의미·상태·동작이 같은 중복 구현은 기존 공용 컴포넌트로 합칠 수 있는가. 겉모양만 같고 저장 시점·권한·작업이 다르면 구분된 변형/컴포넌트가 필요한가. |

error/empty는 목록·폼·비동기 영역에 속할 수 있다. 버튼 하나에 모든 상태를 새로 구현하도록 요구하지 않는다.
정지 이미지에 없는 hover/focus/loading은 누락으로 단정하지 않는다. 스타일 선언이나 래퍼만으로 실제 동작 통과를 선언하지 않는다.
같은 역할의 버튼 위치·이름·아이콘·상태 문구도 비교하고, 공유 수정의 호출 화면과 회귀 위험을 확인한다.

## 결과: 컴포넌트별 표와 영향 범위

종합/컴포넌트 검토에서는 먼저 사용 컴포넌트 목록을 제시한 뒤 아래 표로 결과를 정리한다.

| 컴포넌트 | 현재 문제 | 개선 방향 | 영향 범위(몇 개 화면) |
| --- | --- | --- | --- |
| 실제 컴포넌트명·역할 | 위치·상태·근거 유형·심각도/확신도 또는 확인 범위에서 문제 미발견 | 최소 수정·유지/통합/분리 이유 | 확인한 화면 수와 이름/경로, 미확인 호출 범위 |

화면 수는 라우트·실제 사용 화면과 호출 관계로 확인한다. 같은 화면의 중복 인스턴스·소스 파일 개수를 화면 수로 세지 않는다.
예: ‘확인 3개 화면: 목록/상세/설정, 다른 호출부 미확인’처럼 쓴다. 캡처 한 장에서 제품 전체의 사용 수를 추정하지 않는다.
실제 스타일·행동 차이와 단순한 변형 차이를 분리하고, 같은 공용 원인의 증상은 표 한 행에 묶는다.

## 디자인 토큰은 별도로 정리한다

`토큰 영역(색/간격/라운드/타이포) / 현재 값·혼용 위치 / 권장 기존 토큰·역할 / 영향 화면·확인 조건`으로 별도 정리한다.
토큰 파일과 테마가 있으면 이를 기준으로 색 의미, 간격/패딩, 라운드, 글꼴·크기·굵기·행간의 통일 후보를 제안한다.
일회성 차이와 여러 화면에 반복되는 차이를 구분한다. 적절한 기존 토큰/variant를 먼저 재사용하며 실제 반복 필요가 있을 때만 새 토큰이나 분리를 제안한다.
다크/라이트·활성/호버/포커스/비활성의 결과를 확인한다. 원본 토큰·계산된 색이 없으면 관찰/추정으로 남기고 정확한 색·수치·대비를 만들지 않는다.
